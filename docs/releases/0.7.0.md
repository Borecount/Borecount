## Added public reads

- `GET /v1/holds`: list active and terminal holds; recover a reservation by exact reference.
- `GET /v1/holds/{id}`: inspect original/remaining amounts, state and lifecycle timestamps.
- `GET /v1/holds/{id}/entries`: read original reservation entries.
- `GET /v1/holds/{id}/captures`: inspect successful capture transactions and amounts; capture IDs are transaction IDs.
- `GET /v1/holds/{id}/credit-allocations`: inspect original grant reservations.

Core exposes the corresponding `HoldService.getById`, `list`, `listEntries`,
`listCaptures` and `listCreditAllocations` methods and typed query/read contracts.
Both framework adapters use the shared HTTP DTOs and validation.

Every collection uses the existing JSON `where`, `limit` (default 50, maximum 200),
opaque `cursor`, and `{ data, next_cursor }` envelope. Rows are ordered by ID
ascending. Cursors bind to resource, tenant, parent hold where applicable, and
filters. Missing and foreign parent holds have the same safe not-found response.

Account filters on the hold list describe membership in original entries:
`eq` requires an account, `in` requires any listed account, and `ne` excludes that
account. State-filtered pages reflect committed state at each read; they are not
a frozen cross-request database snapshot.

Original allocation amounts remain immutable after capture or void. They do not
represent current grant availability or current reserved capacity. Read capture
consumption through the existing transaction credit-lineage APIs. Do not derive
captured amount as original minus remaining: void also sets remaining to zero.

## Breaking change and upgrade

Custom implementations of `HoldApplicationRepository` must add the required
`findById`, `list`, `listEntries`, `listCaptures` and `listCreditAllocations` methods.
Implement the exported persistence-neutral read/query contracts, tenant isolation,
parent existence checks and scoped pagination. This port extension is a breaking
public TypeScript change, permitted in a minor release by the pre-1.0 policy.

Consumers using the provided PostgreSQL adapter receive these implementations.
Upgrade the complete five-package set together to `0.7.0` and regenerate the
consumer lockfile. Existing HTTP endpoints and create/commit/void behavior,
idempotency and financial lifecycle rules are unchanged; reads do not create a
second financial authority.

## Database and operations

The published baseline is `0.6.0`. No migration filenames, SQL, metadata or schema
changed from that baseline. No data conversion or new migration is required for
this release; existing clean-chain and backup/restore checks remain applicable.

The separate reference demo migration must pin the coordinated published release,
refresh its OpenAPI/client snapshot and lockfile, and pass its consumer checks
before deployment. Publication of this library does not deploy the demo.
